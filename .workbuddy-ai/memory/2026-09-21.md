策略新增可配止损口径 `stop_mode`：pct（原）/ atr（成本−k×ATR(20)）/ low（入场时盘整下沿×0.98），
以及 `min_hold_days`（最短持仓期内不止损，跌破 12% 紧急线除外）。五变体 × 四窗口（含样本外）重跑：

## 第三轮迭代：降换手（最后一轮）

变体：3只×33% / 2只×50% / 持仓40日 / 持仓60日 / 3只+持仓40日；窗口 = 1y + oos（唯一独立）。

- 近一年全部改善（-5.86% ~ -11.81% vs 基准 -12.96%），但 **样本外熊市全部转负（-2.64% ~ -9.62% vs 基准 +1.24%）**。
- **反直觉：减少同时持仓数反而提高换手**（4只 9.8x → 3只 11.1x → 2只 13.3x，成本 4.63%→6.26%）。
  仓位越集中，单笔出场释放的资金越快被下一只填满，全年笔数不降反升。
- 拉长持仓确实降换手（60日：9.8x→7.2x，成本 4.63%→3.40%），但毛收益仍 -3.70% → **降成本救不了负 alpha**。
- **三轮迭代（调阈值 / 换止损 / 降换手）共 11 个变体，在唯一不重叠的窗口上无一例外变差。**
  判定：信号本身在 A 股无 alpha，**停止调参**；下一步要么换买点形态（trend_buy 的回踩确认结构），
  要么降级为弱市防守型卫星信号。

## 第四轮迭代：换入场结构（突破当天追 → 回踩缩量确认）（2026-09-21 晚）

策略新增 `entry_mode`：`breakout`（原，放量突破当天追）/ `pullback`（突破后回踩缩量确认才买）。
回踩逻辑：`_register_signals` 突破日只登记 `pending`，之后 `pullback_window` 天内回踩到突破位 ±`pullback_band`(3%)、
成交量缩到 `pullback_vol_shrink`(0.6) 以下、站稳 MA10 才买，超窗作废（`_enter_pullback`）。

**结果：这是四轮里首次在四个窗口全部优于基准 config**（基准 = 放量突破当天追）：
- 回踩确认3日窗口（entry_mode=pullback, pullback_window=3）：
  1y +20.63%(基准-12.96%) / oos +10.05%(基准+1.24%) / 2y +7.34%(基准+4.98%) / choppy +19.57%(基准+5.67%)
  夏普 1y 1.71 / oos 1.76 / choppy 1.44；胜率 1y 62.8%、oos 69.2%；oos 盈亏比 2.59；换手 1y 9.8x→6.0x、oos 3.4x→1.9x。
- 全窗口回踩确认（window=5）在 2y +2.51% < 基准 +4.98% → 露破绽；缩量0.4 在 oos -2.53% 转负。
  **只有 window=3 四窗口全优**，是从 5/3、band 3%/5%、vol-shrink 0.6/0.4 小网格里挑的 → 有选择偏差。

**机理**：直击第四节「34% 五日内止损=假突破」根因，等回踩缩量确认挡掉诱多。

**三块硬伤（维持 enabled:false，不擅自改默认 yaml）**：
1. 强牛市仍跑输指数：2y +7.34% vs 沪深300 +41.03%（超额 -33.7pp）——过滤假突破也过滤了真突破主升浪。
2. 那个 oos 熊市窗口此前已用于证伪前三轮（同一测试集二次利用），不算全新样本外 → 选择偏差。
3. `pullback_window=3` 是网格挑出来的，可能只适配近几年节奏。

**全新样本外复验（已跑，结论反转！）**：在从未检视的 2022 熊市、2020-2021 牛市两个窗口复验——
回踩确认3日窗口在 2022 仅 +1.79%（基准 +9.12%，落后 7.3pp）、2020-2021 仅 +2.68%（基准 +29.18%，落后 26.5pp），
两个全新窗口**全部大幅落后基准**。pullback 在 2022 只成交 8 笔（过度保守），在 2020-2021 毛收益 +9.20% vs 基准 +34.88%（滤掉真突破主升浪）。
→ **第四轮同样被证伪**：`pullback_window=3` 就是过拟合到 2023-2026 行情（从该 4 窗口的 5/3 网格挑出，且熊市窗属 seen data）。
→ **结论收回**：原「停止调参」正确，根因更深——该公式信号在任意形态/阈值下都无稳健 alpha。yaml 维持默认 `breakout`+`enabled:false`，**不提 pullback 为默认**。

**方法论沉淀（本会话最强收获）**：本项目验证改动不能只看「调参窗口」和「重叠窗口」，也不能只看
「曾用于证伪他人的窗口」（那也是 seen data）。真正的独立确认 = 一个**从未检视过**的窗口。
本次最干净的过拟合示范：第四轮结构改动在前 4 窗口全胜、在"证伪过前人的熊市窗"也转好，却倒在 2 个真正没看过的窗口上。
前三轮共 11 变体在该熊市窗全败；第四轮在 2 个全新窗全败——四轮 16+ 变体无一在全新样本外稳定优于基准。

## 20:20 后端启动报「数据库由其他进程持有」排查 + 启动脚本加固
- 现象：`./scripts/start_backend.sh` 后 uvicorn startup 失败：
  `qmt_trade/storage/duckdb/database.py:89 RuntimeError: 数据库由其他进程持有`
  （`__init__` 用 `open(path,'rb')` 探文件头时撞上 DuckDB 独占锁 → PermissionError）。
  13:59 与 19:49 两次重启都失败；13:37 那次实例正常。
- 根因：`data/db/qmt.duckdb`（约 926MB）**同一时刻只允许单进程持有**；
  旧脚本只 taskkill 端口占用者 + sleep 2，**若旧进程已不在 LISTEN（卡住/启动失败残留）
  就杀不到它**，它继续持锁 → 之后每次重启都失败。20:13 复查已无 python 进程、文件可读（DUCK 头）。
- 加固 `scripts/start_backend.sh`：
  1) 端口占用者改 `taskkill //T //F`（连子进程树，防 spawn 的回测计算进程变孤儿）；
  2) 用 psutil 按 cmdline `server.main:app` 扫**未监听端口的孤儿后端**并杀掉；
  3) 启动前轮询等待文件锁释放（最多 30s），仍占用则打印明确错误与排查命令后 exit 1。
  4) 踩坑：`set -e` 下写 `[ "$WAIT" -gt 0 ] && echo ...` 会在 WAIT=0 时让脚本静默退出，
     必须改成 `if ... then ... fi`。
- 实测：另起进程独占 duckdb 时，脚本会等待并打印「数据库锁已释放（等待 Ns）」后正常启动。
- **重要**：WorkBuddy 沙箱里用 Bash 启动的后端进程会在命令/后台任务结束时被回收，无法常驻
  （实测健康检查 200 后随即消失）。要常驻必须在用户自己的 MINGW64 终端里跑
  `./scripts/start_backend.sh`（或开机自启 `scripts/autostart_backend.bat` → watchdog）。
