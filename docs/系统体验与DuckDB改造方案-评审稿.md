# 系统体验与 DuckDB 改造方案（评审稿）

日期：2026-09-13  
状态：待评审，尚未实施  
范围：数据存储与性能、WebUI、策略配置、异步回测、运行模式、废代码清理。

> 本轮只提交方案。下述目录、表、接口、性能指标均为拟议设计，不代表已经实现或测试通过。评审通过后按阶段实施，不在本轮修改业务代码、迁移数据库或删除文件。

## 1. 改造目标与结论

把日常使用收敛成三条主线：**查看账户和运行状态 → 配置并启用策略 → 选择策略与周期回测、收到报告**。

1. DuckDB 成为业务数据、行情、缓存、任务和报告的唯一运行时持久化数据库；移除 SQLite 和 JSON 文件存储链路，同时收敛现有 Parquet 分片缓存。
2. 保留现有 Python / FastAPI / Vue 3 / Pinia 技术栈，重构数据访问、任务执行和界面组织，不进行无关框架替换。
3. 策略默认展示不超过 8 个核心输入，复杂参数按组折叠；普通使用不要求编写 JSON/YAML。
4. 回测只要求选择策略和日期区间，后台排队执行、持久化进度和结果，离开页面后仍能运行并收到站内通知。
5. 系统运行模式只保留模拟盘 `paper` 和实盘 `live`；回测是任务，不是第三种运行模式。
6. 清理以“无引用、已替代、回归通过”为依据，避免把仍在复用的页面或交易安全逻辑当成废代码删除。

**关键技术决策：采用单一数据库所有者进程访问运行库，回测通过独立计算进程运行。** DuckDB 替换不能仅修改连接字符串；需要同时解决进程访问边界、批量写入、SQL 方言和后台任务恢复。

## 2. 现状核查与问题依据

本方案依据当前工作区代码静态核查形成，未连接券商、未启动交易、未进行真实性能压测。因此下表区分已发现的代码事实和需要实测验证的影响。

| 范围 | 已确认的现状与代码位置 | 改造方向 |
|---|---|---|
| 业务数据库 | `qmt_trade/storage/db.py` 使用 SQLite、WAL、线程局部连接和实例锁；单条 `execute` 回滚残留事务后执行并提交 | 重写事务契约，避免逐条提交；不得照搬旧事务包装 |
| SQL 兼容 | `storage/db.py` / `models.py` 使用 `lastrowid`、`rowcount`、`AUTOINCREMENT`、`sqlite_master`、`PRAGMA` | 逐项替换并验证幂等、主键、迁移和返回值语义 |
| 行情文件 | `datahub/store.py` 的 `read` 先读文件再过滤日期；`upsert` 读取旧分片、合并、去重后整体重写 | 改为数据库条件下推、列裁剪、增量批量入库 |
| 多套磁盘缓存 | `datahub/manager.py` 使用 Parquet + JSON 元数据；QMT/Akshare provider 各有 Parquet 缓存 | 统一行情表、来源和缓存元数据，消除重复存储实现 |
| LLM 缓存 | `brain/llm/cache.py` 单独使用 SQLite | 纳入 DuckDB 缓存仓储 |
| 零散 JSON | 策略有 JSON 文件读取，通知有 JSON 行文件写入；策略实例和部分状态以大 JSON 存在 `system_state` | 区分文件持久化与传输编码，将查询字段结构化 |
| 后台任务 | `server/context.py` 用内存 `JOBS` 字典，每个任务新建 daemon 线程 | 持久化任务、限制并发、隔离计算、恢复中断状态 |
| 通用回测 | `server/schemas.py` 的 `BacktestIn` 无策略字段；`routers/backtest.py` 未传策略，结果截取前 1000 个曲线点 | 统一策略入口；保存完整结果，展示用覆盖全区间的降采样 |
| 其他回测 | `routers/strategylab.py` 已支持指定独立策略/版本；另有 `tail_pick` 入口，返回结构和保存方式不统一 | 复用已有回测能力，统一调度、结果、历史报告 |
| 回测交互 | `BacktestView.vue` 每 1.5 秒查询任务并刷新列表，卸载后停止轮询；比例指标按数值大小猜单位 | 全局任务通知；字段明确单位和精度 |
| 策略编辑 | `StrategyView.vue` 用 JSON 文本编辑实例参数，已有草稿、发布和回滚 | 保留版本能力，用分层表单替换 JSON 主流程 |
| 配置生效 | `server/context.py` 保存后清空上下文缓存，但注释明确调度器可能仍持有旧实例 | 增加配置版本和运行版本确认，解决保存与执行状态脱节 |
| 页面组织 | 顶层入口较多；全局模式选择与两条交易路由并存；设置页复用旧子页面 | 减少入口，统一模式来源，按工作流组织页面 |
| 模式收敛 | 当前 CLI choices 与顶部选项已是 paper/live；README 和部分注释仍有 sim，研究请求存在 live→paper 改写 | 做一致性收尾，不能误称全部入口仍有三模式 |

需要基线测试进一步定位：行情下载等待、QMT 调用串行化、因子重复计算、账户查询、健康检查、页面重复请求、CPU/磁盘竞争各占多少时间。**不预设“全部卡顿都是 SQLite 导致”，也不承诺换库后所有查询天然更快。**

工作区已有未提交修改：`qmt_trade/app.py`、`tests/smoke_scheduler.py`、`webui/src/configHints.ts`。实施时先确认并保留这些修改，不覆盖或回退。

## 3. DuckDB 存储方案

### 3.1 存储边界

| 内容 | 目标落点 |
|---|---|
| 订单、成交、持仓、账户快照、风控、对账、调度记录 | DuckDB 业务表 |
| 行情、分钟线、财务、因子、新闻、交易日历、数据覆盖情况 | DuckDB 数据表 |
| 策略实例、参数版本、运行状态、观察列表、研判记录 | DuckDB 结构化表 |
| LLM 缓存、行情缓存元数据、TTL、来源与校验信息 | DuckDB 缓存表 |
| 异步任务、进度、通知、报告指标、完整净值与成交明细 | DuckDB 任务及结果表 |
| 内置默认参数、部署启动配置 | 保留版本管理下的 YAML；用户在页面保存的业务配置以数据库版本为准 |
| 密钥 | 保持环境变量 / `.env`，不迁入普通业务表 |
| HTML/Markdown/CSV 等报告下载 | 允许按需导出；系统历史查询直接读数据库，不扫描导出文件 |
| 程序日志 | 保留轮转文本日志；业务事件和通知历史进数据库 |

“不再使用 JSON 文件方式”指不再用 JSON/JSONL 文件作为业务存储或缓存。HTTP JSON、代码序列化、`package.json` 等工程文件不属于清理目标。数据库中可保留用于复现的参数快照 JSON 字段，但状态、时间、策略、模式、指标等常查字段独立成列，不能把全量业务继续塞进一个 JSON 字段。

现有 Parquet 也退出默认运行链路，避免出现“数据库换了，行情仍在遍历碎文件”的半迁移。它只可作为旧数据导入来源或用户显式导出的交换格式。

### 3.2 文件和进程布局

首版使用一个运行库 `data/db/qmt.duckdb`，按 schema 分隔：

- `market`：共享行情、财务、事件、数据版本。
- `trading`：账户与交易状态，强制使用 `mode + account_id` 隔离。
- `strategy`：定义元数据、实例、配置版本、运行版本。
- `jobs`：任务、尝试次数、进度事件、站内通知。
- `research`：研判、回测运行、净值、成交、指标和报告。
- `cache`：缓存条目、来源、有效期。
- `meta`：数据库版本、迁移清单、配置版本和数据集版本。

```text
WebUI / CLI
     │ HTTP（CLI 在线模式也经过服务）
     ▼
FastAPI + 调度器 + StorageService（唯一运行库所有者进程）
     ├── 有界读任务 + 各线程独立连接/游标
     ├── 写入队列 + 显式短事务 ── qmt.duckdb
     └── 回测调度 ── 独立计算进程（默认 1 个）
                       │ 专属 DuckDB 输入快照/临时结果库
                       └── IPC 进度及结果引用 → 所有者验证并导入
```

具体约束：

1. 运行库不允许 Uvicorn 多 worker、CLI、外部回测进程各自直接打开；启动检测所有权冲突并给出可理解的错误。
2. 首版所有者与 API 同进程，以线程执行阻塞数据库操作；CPU 密集回测移出该进程。未来需要多 API 实例时再把 StorageService 独立成服务。
3. CLI 在线操作调用服务；离线维护必须取得排他所有权，确认服务已停止。保留 CLI 能力，但不保留多进程抢写文件的实现。
4. 回测输入由所有者按所需股票、区间、预热数据导出专属 DuckDB 快照。完成并关闭后交给计算进程；计算进程不打开运行库，即使只读也不绕过此边界。
5. 临时结果库由计算进程关闭后再导入；按任务和校验摘要幂等导入，报告落库成功后才将任务标记成功。
6. 交易写入优先于批量入库；大批次分段提交并设置队列上限。订单持久化必须等待提交确认，不能当作可丢弃缓存异步处理。
7. 行情和账户缓存设独立有效期；交易前校验使用当前有效数据，不能为了界面流畅无限复用过期报价。

DuckDB 原生文件读写的并发边界主要在单进程内，官方也介绍了远程协议等其他方案；本项目首版选择原生文件 + 明确所有者，避免引入额外数据库服务栈。依据：[DuckDB Concurrency](https://duckdb.org/docs/current/connect/concurrency)。

### 3.3 数据模型与访问接口

优先保留现有 Repo 的业务接口，替换内部 SQL 和事务实现；新增 `MarketRepository`、`StrategyRepository`、`JobRepository`、`BacktestRepository`，业务层不再自行读写文件。

| 表组 | 关键设计 |
|---|---|
| bars / fundamentals / factors | 标的、频率、时间、复权方式、来源、可见时间、数据版本；按实际实体定义唯一键 |
| orders / trades / positions | 模式、账户、业务 ID；订单幂等键唯一；持仓含策略归属，不混用模拟和实盘 |
| strategy_instances / versions | 实例和模式分离标识；不可变版本；草稿、发布版本、实际运行版本独立 |
| jobs / attempts / events | UUID、状态、阶段、计数、心跳、取消标记、错误码、输入摘要、重试关系 |
| backtest_runs / metrics / equity / trades | run_id 关联；完整曲线带日期；指标单位明确；记录参数、数据、代码和成本模型版本 |
| cache_entries / dataset_coverage | 来源、键、时间范围、TTL、缺口、质量状态；不依赖旁路 JSON |
| notifications / reports | 任务引用、已读状态、报告版本；关闭页面后仍可查询 |

PIT 数据必须区分“业务发生时间”和“当时可见时间”。财报修订、复权版本、新闻发布时间不能在迁移时被简单覆盖成最新值。未知历史可见时间的记录要标记来源与局限，不能伪造 PIT 完整性。

SQL 适配包括：自动 ID 改为 UUID 或显式 sequence；插入返回值改为 `RETURNING` 等明确契约；替换 SQLite 元数据查询；核对布尔、日期、时区、NULL、唯一约束和 upsert 语义。持仓更新、订单状态和成交落库按业务事务组织，事务内部禁止偷偷自动提交或回滚。

### 3.4 入库与查询性能

- 行情采用批量 DataFrame/Arrow 注册后集合写入、分批 upsert；不做逐行独立事务。官方建议使用批量导入而非逐行插入：[DuckDB Data Import](https://duckdb.org/docs/lts/guides/performance/import)。
- 按标的、频率、日期、复权和可见时间在 SQL 中筛选，只读需要列；列表使用稳定排序和分页。
- 按常见查询条件组织装载顺序，通过 `EXPLAIN ANALYZE` 判断扫描量；索引只对已证明有收益的定位查询添加。
- 合并同一批任务重复下载与因子请求；按数据版本、参数摘要、asof 构造缓存键，限制容量和 TTL。
- 下载、解析、入库、因子计算分段计时；QMT 调用保留既有超时与线程约束，由统一适配器调度，不盲目增加并发。
- 为查询、回测、入库分别设置内存、线程和超时预算；避免 DuckDB 查询与回测同时吃满 CPU。
- 账户与健康状态由后台定时刷新并记录更新时间，普通 GET 查询返回快照；健康状态改变和必要交易前校验由明确流程处理。

### 3.5 迁移、校验与回退

1. **只读盘点**：枚举实际数据库、表、JSON/JSONL、Parquet、数据量和引用，不只根据扩展名猜测用途。先生成迁移清单和空间估算。
2. **副本试迁移**：将 SQLite、JSON、Parquet 导入新库；迁移程序可以只读使用 SQLite，正式运行依赖不得再使用它。
3. **转换规则**：共享研究数据与 paper 账本拆分归类；保留原 ID/时间/来源；歧义、重复主键和坏文件进入隔离清单，不静默丢弃。
4. **核对**：各实体记录数、主键集合、订单状态、成交额、持仓数量和成本、账户余额、最早/最晚日期、按分区摘要逐一比对。不可只检查总行数。
5. **性能与语义回归**：旧副本与新库运行固定查询和离线回测，对比结果；确认字段精度、排序与交易幂等不变。
6. **正式切换**：停止新增任务和交易提交，等待/终止可中断研究任务，停止旧写入，对未完成订单对账；生成一致性备份并完成最终增量迁移。SQLite 备份使用一致性机制，不能只复制可能依赖 WAL 的主文件。
7. **切换后验收**：配置原子切换到新库；先验证模拟盘、数据更新和任务恢复，再进入实盘验收。正式运行不保留 SQLite 双写或自动 fallback。
8. **回退边界**：未产生新写入时可恢复旧应用与一致性备份；产生新订单/成交后必须停交易、对账并迁回新增记录，禁止直接换回旧库遗漏成交。执行过的订单不得自动重发。
9. **清理**：旧数据备份按建议 30 天保留期归档，验收后移除运行时旧存储实现；备份到期再按明确清单清理，不在切换时删除原始数据。

## 4. WebUI 布局与交互

### 4.1 一级导航收敛为六项

| 新入口 | 页面内容 | 现有入口去向 |
|---|---|---|
| 工作台 | 账户摘要、运行状态、策略状态、待处理事项、最近任务 | Dashboard 汇总；不再展示大段原始对象 |
| 交易 | 持仓、委托、成交、账户及风控状态 | paper/live 共用一条交易页面，模式由顶部控制 |
| 策略 | 策略列表、配置、启停、版本、最近回测 | 策略管理与实验室合并；扫描/进化放高级工具 |

顶部固定：项目名称、模拟盘/实盘切换、连接状态、任务通知、紧急停止入口。实盘状态显著标识；切换查看模式不自动启动交易或解除风控锁定。

### 4.2 统一交互规范

- 每页一个清晰标题和主按钮；查询条件放工具栏，详情用抽屉或详情页，减少多层弹窗。
- 首屏先呈现主要信息，耗时区块独立加载；显示骨架、空状态、失败原因和重试入口。
- 中文字段名、单位、范围和简短帮助；百分比、金额、比率由指标元数据格式化，不能按数值大小推断。
- 表格默认 20～50 行、服务端分页；大量行情点降采样；必要时虚拟滚动。
- 页面切换取消失效请求；同键请求去重；筛选防抖约 300ms；旧模式响应不得覆盖新模式页面。
- 状态轮询集中管理，同一任务只保留一个订阅；后台标签页降频，keep-alive 页面停用时暂停无用刷新。
- 顶部任务中心全局常驻，离开回测页不影响进度；通知错误不连发相同 toast。
- 保留现有路由懒加载；设置内页按需加载。刷新后保留筛选和任务定位，浏览器只存界面偏好。
- 适配 1366×768、1920×1080 和窄屏布局；键盘可操作、焦点可见、状态不只依赖颜色。

## 5. 策略配置简化

### 5.1 三层参数界面

| 层级 | 默认状态 | 内容 |
|---|---|---|
| 核心参数 | 展开，最多 8 个输入 | 标的范围、资金/仓位、持仓数量、止损及策略特有的关键选择 |
| 高级参数 | 按组折叠 | 入场过滤、退出细节、时间窗口、成本、因子权重、数据质量阈值 |
| 专家与诊断 | 默认不显示，主动进入 | 参数来源、完整有效配置、调试说明和实验工具 |

保留既有默认值作为初始方案，不借界面改版擅自修改交易行为。未来如加入“保守/均衡”等预设，应作为明确版本并展示参数差异，不能暗中覆盖已有自定义参数。

核心参数建议映射（最终以各策略配置类校验为准）：

| 策略 | 默认展开示例 |
|---|---|
| 趋势买点 | 形态 `pattern`、最大持仓 `max_positions`、单仓比例 `position_fraction`、最大持有天数 `max_hold_days`、止损底线 `stop_floor_pct` |
| ETF T0 | 标的 `symbols`、底仓 `base_fraction`、做 T 比例 `t_slice_ratio`、止损 `stop_pct`、每日交易次数上限 |
| 股票 T0 | 标的/底仓、做 T 额度、止损、每日交易次数；只展示该策略实际支持的字段 |
| 打板/二板/低吸/尾盘选股 | 标的范围、持仓数、单仓比例、止损、持有期限及必要形态选择；按策略差异定义，不强行套同一表单 |
| 多因子策略 | 策略预设、候选/持仓数和资金限制；因子权重与市场状态参数折叠 |

### 5.2 元数据与生效规则

1. 后端提供统一参数 schema：字段、类型、默认值、单位、上下限、分组、级别、依赖、说明和适用策略，前端据此渲染。
2. 对嵌套参数、列表和标的覆盖项提供结构化控件；前后端共同校验范围与组合约束。
3. 折叠只影响展示；保存只更新用户修改字段，保留高级参数，禁止因隐藏字段未提交而回填默认值。
4. 内置 YAML 作为初始化默认和导出模板；数据库保存用户配置及版本。明确优先级：内置默认 → 已发布版本 → 允许的环境覆盖；页面展示最终有效值及来源。
5. 保存草稿与“应用配置”分开。应用时生成不可变版本，调度器在安全边界切换并回报 `running_version`；页面展示“已保存/待生效/已生效”。
6. 已运行回测绑定提交时版本，不能被随后编辑影响；交易处理中不替换上下文。全局硬风控约束不能被策略参数放宽。
7. 支持恢复默认、修改差异和版本回滚；回滚也是一次发布并等待运行确认。

## 6. 回测重构

### 6.1 用户流程

**选择策略 → 选择周期 → 开始回测 → 后台运行 → 站内通知 → 查看报告。**

- 策略选择默认使用该实例当前发布版本；尚无实例时使用内置默认快照，并在页面说明。
- 周期提供近 1/3/6 个月、近 1 年、自定义起止日期；周期指日期范围，日线/分钟线由策略需求确定。
- 初始资金默认沿用现有 100 万并可在高级选项修改；预热长度由因子/策略所需交易日自动推导，不让用户猜。
- LLM 默认关闭，成本参数使用已发布设置；这些值在提交摘要和报告中可见。
- 提交即返回任务 ID；数据缺口自动进入补数阶段，失败显示具体缺失区间、原因和重试动作。
- 已有有效数据但无成交是正常结果，明确“本区间无成交”；数据不足或引擎失败不得伪装成成功报告。

### 6.2 统一服务与能力适配

新增统一 `BacktestService`，通过策略注册表选择适配器：复用通用 `BacktestEngine`、已有 `build_standalone_backtester` 和尾盘策略能力，统一输入/输出协议。首轮不强行重写全部撮合内核，但必须回归不同策略的日期、成本和成交语义。

注册表包含策略 ID、参数 schema、所需数据频率、预热需求、回测能力。无适配器的策略明确不可提交；不能收到策略名后仍执行默认策略。上线目标是覆盖当前全部可交易策略，不能以隐藏不可用策略替代修复。

拟议 API：

| 接口 | 行为 |
|---|---|
| `GET /api/strategies` | 策略、实例、版本和回测能力 |
| `POST /api/backtests` | 接收策略/版本/起止日期/高级覆盖，返回 HTTP 202 + job_id |
| `GET /api/jobs/{id}` | 状态、阶段、进度、错误、report_id；不夹带完整成交历史 |
| `GET /api/jobs?kind=backtest` | 分页任务历史 |
| `POST /api/jobs/{id}/cancel` | 请求协作取消，确认停止后才标记取消 |
| `POST /api/jobs/{id}/retry` | 新建尝试并保留原失败记录 |
| `GET /api/backtests/{id}/report` | 报告摘要、指标、曲线；成交另分页 |
| `GET /api/notifications` | 持久化站内通知和已读状态 |

旧三个回测入口短期代理到统一服务，客户端完成迁移后删除旧实现。默认无须 Celery/Redis；数据库任务表 + 有界计算进程足够覆盖首版单机需求。

### 6.3 任务状态与恢复

状态：`queued → running → succeeded / failed / cancelled`；异常退出的运行任务为 `interrupted`。阶段独立表示“检查数据/下载数据/准备快照/计算/生成报告”。

- 单任务运行、其余排队为默认配置；报告进度按已处理交易日/总交易日计算，下载无总量时显示实际数量，不造百分比。
- 任务先落库再确认提交；领取、尝试编号和心跳受统一事务管理，避免重复领取。
- 前端提交使用幂等请求键，避免双击重复任务；用户主动再跑允许创建新任务。
- 重启后 queued 可继续，失去心跳的 running 转为 interrupted，提供一键重跑。首版不承诺从任意交易日断点续算。
- 取消在可检查边界生效；超时先请求停止，必要时终止专属计算进程并标记中断，不能把仍在运行的线程标记完成。
- 结果导入和成功状态原子提交；通知使用事务 outbox 和唯一事件 ID 重试，失败不丢报告、不重复提示。
- 全局自适应轮询为首版默认：活跃任务约 2 秒、无任务显著降频；请求结束后再安排下一次，避免重叠。后续有需要再加入 SSE。
- 站内通知为必需能力；外部渠道沿用用户已有配置，浏览器关闭时结果仍保存，重新打开可见未读通知。

### 6.4 报告内容与正确性

报告包含策略/参数版本、区间、数据来源和覆盖、初始资金、收益、回撤、胜率、交易数、成本、完整日期净值曲线、成交明细、期末持仓及失败/无成交说明。

展示曲线允许按像素预算降采样，必须保留首尾和重要极值，不能只截取前 N 条。原始结果全部持久化。指标以字段定义单位：收益率显示百分比，夏普/盈亏比显示比率，交易数显示整数，样本不足显示“不适用”而不是伪造 0。

回归包括：PIT、信号与成交时间、交易日预热、复权、停牌和涨跌停、不同品种可用持仓规则、成本、期末浮盈。回测进程只装配模拟执行器，不持有实盘下单能力；研究数据无需通过全局 live→paper 参数改写获得。

## 7. 仅保留模拟盘与实盘

1. 前端类型、后端请求模型、CLI、组合根和文档统一为 `paper | live`；非法值明确拒绝。
2. 浏览器旧 `sim` 偏好清理并回到 paper，给一次迁移提示；后端非法 mode 不静默转换。
3. `SimGateway` 继续用于模拟盘与回测，其名称代表模拟撮合器，不是第三种用户模式。Mock 数据只保留为测试 fixture，不在正式模式菜单暴露。
4. 研究与行情接口逐步移除不必要的 mode 参数；涉及账户/实例归属的接口明确模式。删除含糊的自动降级与请求改写。
5. 模式切换原子更新路由、状态和查询键；切换后清空旧账户展示，旧请求不能回填。旧 `/trade/paper`、`/trade/live` 路径迁移到统一交易页并显式设置对应模式。
6. 实盘连接、授权、账户隔离、幂等和风控闸门保留。停止交易、只减仓、锁定属于运行状态，不增加模式选项，也不能作为“其他模式”误删。

## 8. 清理与项目结构

清理候选：旧 SQLite 运行适配、旧 Parquet/JSON 缓存实现、重复回测路由和结果处理、孤立页面、过时 sim 文案、一次性诊断脚本、失效配置项、构建缓存和误生成文件。

执行顺序：引用扫描 → 动态注册/CLI/调度器/测试调用核查 → 标记替代入口 → 回归 → 删除。输出删除清单、依据和替代位置。

特别说明：`ConfigView.vue`、`DatasourceView.vue`、`LlmView.vue`、`NotifyView.vue` 仍被设置页引用，不能因为路由重定向就直接删除；历史报告和真实交易数据不是废代码；`tests/` 中研究脚本要先区分工具与自动测试。根目录 `nul`、备份和缓存目录先核实来源，不按名称直接批量删除。

拟议新增目录：`qmt_trade/storage/duckdb/`、`qmt_trade/tasks/`、`qmt_trade/backtest/service.py`、`scripts/migrations/`、前端通用参数表单和任务中心组件。避免为了目录美观移动全部现有模块。

## 10. 验收标准

### 10.1 功能和使用体验

- 运行时业务数据仅使用 DuckDB；SQLite 仅能出现在明确的旧数据导入工具中；无 JSON/JSONL/Parquet 缓存落盘链路。
- 新用户无需编写 JSON，在策略页完成配置、保存、应用并看到实际生效版本；默认核心输入不超过 8 个，高级默认折叠。
- 从回测页用“策略 + 周期 + 提交”完成任务；切页、刷新、关闭浏览器不丢任务和报告；服务重启能正确显示中断并重跑。
- 回测选择的策略/版本与实际引擎输入一致；结果与报告可追溯；无成交与失败状态区分。
- 仅 paper/live 两种模式，模拟数据不进入正式回测；模拟/实盘账户和交易写入严格隔离。
- 页面无旧模式串数据、无悬空加载、无整页长时间白屏，失败可恢复。

### 10.2 性能目标（待 P0 实测确认的工程目标）

统一同机器、同数据、同查询条件比较，分别记录冷启动、热缓存和运行回测时的 p50/p95、CPU、峰值内存、磁盘量。网络下载耗时单列，不用缓存命中时间冒充首次补数速度。

| 项目 | 拟定目标 |
|---|---|
| 本地常用列表/账户快照查询 | p95 ≤ 300ms，回测并行时 p95 ≤ 500ms |
| 回测任务提交 | 不等待下载/计算，p95 ≤ 500ms 返回持久化任务 ID |
| 缓存完备时主要页面可操作 | ≤ 1.5 秒；普通交互反馈 ≤ 100ms |
| 单标的历史曲线查询 | 约 5 年日线，p95 ≤ 300ms |
| 批量行情入库 | 同数据基线下争取 ≥ 3 倍吞吐；没有基线不得宣称达成 |
| 多标的历史筛选 | 同数据基线下争取 ≥ 3 倍改善，记录扫描行数与执行计划 |
| 回测计算 | 同策略、同数据、同参数的离线计算争取减少 ≥ 50% 耗时；结果语义不变优先 |
| 任务通知 | 后台完成提交后，前台活跃页面一般 3 秒内可见 |

基准样本建议：实际全量数据 + 固定 100 万行日线/1000 万行分钟线副本、500 标的区间查询、1000 行以内常用业务列表；至少 30 次短查询重复，并单独记录冷缓存。若实际数据不足，合成数据只用于性能测试，绝不用于收益报告。任何目标调整要说明硬件、数据规模和测量依据。

### 10.3 必要验证

- 存储：迁移对账、事务回滚、重复订单键、账户隔离、批量去重、重启持久性、单所有者冲突、缓存失效。
- 回测：确定性小数据样本、既有策略历史回归、跨区间净值、取消、进程崩溃、结果导入失败、通知去重。
- 配置：核心/高级字段往返不丢值、错误范围、版本生效、回滚、提交后参数不漂移。
- 前端：`npm run typecheck`、`npm run build`；浏览器验证核心流程、窄屏、模式切换与慢请求。
- 复用现有 `smoke_backtest.py`、`smoke_webui_api.py`、`smoke_scheduler.py`、`test_strategy_lab.py`、缓存相关测试等；先核对运行前提。需要真实 QMT 的验证单列，未运行不得写为已通过。
- 全面改造验收不以真实下单作常规测试；实际实盘切换安排在停机、迁移和对账流程内。

## 11. 评审决策清单

建议整体批准以下设计后再执行：

1. DuckDB 唯一运行库，连同现有 Parquet/JSON 缓存一并收敛；保留部署 YAML、密钥和导出文件边界。
2. 单所有者进程 + 默认单回测计算进程；CLI 通过服务访问运行库，离线维护使用排他模式。
3. 六项一级导航，交易统一页面，回测统一入口，策略实验室收进策略高级功能。
4. 核心参数不超过 8 项，保留现有默认行为，高级参数折叠且不丢失，参数版本能追踪到实际执行。
5. 任务持久化、完整报告、站内通知为首版必做；任意进度断点续跑不纳入首版。
6. 按 P0～P5 分阶段交付；数据备份先保留、验证后清理，禁止未核实引用就批量删除。

评审意见可以直接按章节编号修改；通过前不执行迁移、业务重构或删除操作。
