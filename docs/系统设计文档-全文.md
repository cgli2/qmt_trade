## 2. 项目目标与边界

### 2.1 目标

构建一个 A 股全自动交易系统，能够在**无人值守**的情况下完成：数据采集 → 因子计算 → 自动选股 → LLM 深度研判 → 风控校验 → 仓位计算 → QMT 自动下单 → 持仓监控 → 盘后复盘 → 策略进化。

### 2.2 明确的非目标（本期不做）

- 不做港股 / 美股 / 期货 / 期权（架构预留，不实现）
- 不做高频（Tick 级套利、做市）——QMT 普通账户不具备条件
- 不做多账户 / 资管
- 不做 Web 前端（M0-M3 阶段用 CLI + 日报 + 消息推送；前端后置）

### 2.3 成功指标

分阶段定义，避免一开始就追求不现实的目标：

| 阶段 | 指标 |
|---|---|
| 回测阶段 | 3 年样本外年化 > 15%，最大回撤 < 20%，夏普 > 1.0，换手可承受 |
| 模拟盘阶段 | 连续 3 个月模拟盘，实际成交与回测偏差 < 20%（滑点模型有效性验证） |
| 小资金实盘 | 3 个月，回撤不超过模拟盘的 1.5 倍，无重大执行事故（错单/超买/失联） |
| 系统可用性 | 交易日 09:15–15:00 可用性 > 99%，任何异常必须**失败安全**（停止开仓而非乱开仓） |

### 2.4 【风险】关于"高胜率机器自动炒股"的现实预期

这一节请务必在评审时讨论，我认为这是项目最大的认知风险。

1. **胜率 ≠ 赚钱。** 一个 80% 胜率、每次赚 1% 亏 5% 的策略是稳定亏钱的。系统的优化目标应当是**期望值和夏普**，不是胜率。文档后续所有设计都以此为准。
2. **LLM 不产生 alpha，它压缩信息。** LLM 的价值在于：把非结构化信息（新闻、公告、研报、龙虎榜、互动易）快速转成结构化判断，以及做多角度交叉验证。它不会因为"更聪明"就预测出价格。指望 LLM 直接选出涨停股是不现实的。
3. **【风险】LLM 历史回测天然被污染。** 大模型的训练数据包含了历史行情和新闻，让它回测 2023 年的行情，它"知道后来发生了什么"。**这个问题无法根除。** 因此本设计的态度是：LLM 层以**前进式模拟盘验证**为主，历史回测只做健全性检查（详见 6.10）。
4. **A 股的硬约束**：T+1、涨跌停、停牌、印花税单边 0.05%（2023 年后）、滑点与冲击成本。这些在回测里必须真实建模，否则回测收益全是假的。
5. **建议的期望值**：先做到"稳定小赚、回撤可控、系统不出事故"，再谈放大。上线路径为 回测 → 模拟盘 3 个月 → 实盘 ≤10% 资金 3 个月 → 逐步放大。

## 3. 核心设计原则

这 7 条是后续所有模块设计的依据，评审时如有异议请先在这里推翻。

**P1. LLM 只做分析与仲裁，绝不直接下单。**
LLM 的输出是 `TradeIntent`（交易意图），不是订单。所有涉及金额、数量、价格的计算由确定性代码完成。理由：LLM 有幻觉、不可复现、算术不可靠，而金额计算错误的代价不可逆。

**P2. 双时钟：慢思考做计划，快执行不调 LLM。**
盘前/盘后跑 LLM（延迟 10–60s 可接受），产出带触发条件的交易计划；盘中由确定性引擎按计划执行（毫秒级）。只有重大事件才走 LLM 快速通道，且必须有超时和降级。

**P3. 风控是硬闸门，LLM 无权否决。**
规则引擎优先于 LLM。LLM 可以提出风险点，但"能不能下这一单"由规则说了算。任何 LLM 输出都要过一遍不可绕过的 Pre-trade 检查。

**P4. 失败安全（Fail-Safe），不是失败开放。**
任何组件异常（数据源挂了、LLM 超时、QMT 断连、账户对账不平），系统的默认行为是**停止开仓、保留平仓能力**，而不是继续交易。

**P5. 先跑通无 LLM 的确定性闭环，再叠加 LLM。**
M1 阶段必须有一个纯规则/因子的完整闭环能跑通回测和模拟盘。LLM 是这个闭环上的"增强插件"，可以一键关闭。这样 LLM 失效时系统仍然能活。

**P6. 一切可回放、可审计。**
每个决策都要能回答"当时为什么这么做"：输入数据快照、prompt、LLM 原始响应、风控判定过程、最终订单，全部落库。LLM 调用做 `prompt_hash → response` 缓存，用于回测确定性重放。

**P7. 回测与实盘共用同一套代码路径。**
成本模型、风控引擎、仓位引擎、执行服务在回测和实盘中是同一份代码，只有数据源和订单出口不同。qmt_etf 回测未计滑点导致的失真，就是反面教材。

## 4. 总体架构

### 4.1 分层架构

```
┌──────────────────────────────────────────────────────────────────────┐
│  L6  运维层   CLI / 日报 / 企微·钉钉告警 / Kill Switch / (后置)Web UI  │
├──────────────────────────────────────────────────────────────────────┤
│  L5  进化层   复盘归因 → 经验库 → 参数寻优(walk-forward) → 策略池调权   │
├──────────────────────────────────────────────────────────────────────┤
│  L4  执行层   ExecutionService  →  OrderGuard  →  QMT Gateway         │
│              (统一下单/撤单)      (防重/幂等)      (xtquant 封装+重连)  │
├──────────────────────────────────────────────────────────────────────┤
│  L3  风控仓位  RiskEngine (Gate1前置/Gate2持仓/Gate3盘后)              │
│               PositionSizer (风险预算法 + 波动率/置信度调整)            │
├──────────────────────────────────────────────────────────────────────┤
│  L2  决策层   ┌─ 规则选股漏斗 (L0粗筛→L1因子精排)  ← 不依赖 LLM        │
│               └─ LLM 研判 (L2 多智能体) → TradeIntent  ← 可一键关闭    │
├──────────────────────────────────────────────────────────────────────┤
│  L1  特征层   因子引擎(量价/资金/基本面/情绪) + 市场状态识别(Regime)     │
├──────────────────────────────────────────────────────────────────────┤
│  L0  数据层   DataHub: QMT/xtdata + Tushare + AkShare                 │
│               统一接口 / 优先级降级 / PIT时间切片 / 分层缓存            │
└──────────────────────────────────────────────────────────────────────┘
        ↕ 横切：配置中心 · 日志 · 事件总线 · 调度器 · 存储 · 成本控制
```

### 4.2 关键架构决策记录（ADR）

| ID | 决策 | 备选方案 | 理由 |
|---|---|---|---|
| ADR-1 | LLM 输出 Intent 而非 Order | LLM 直接产出订单 | P1；金额计算不可交给 LLM |
| ADR-2 | 双时钟（慢决策/快执行） | 盘中实时调 LLM | LLM 延迟 10–60s，盘中不可用；且成本不可控 |
| ADR-3 | 三级选股漏斗，LLM 只处理 Top50-100 | LLM 扫全市场 | 5000 只票全用 LLM，每天成本上千元且延迟不可接受 |
| ADR-4 | 单进程多线程 + APScheduler | 微服务 + 消息队列 | 单账户单机场景，微服务是过度设计；但模块边界按可拆分设计 |
| ADR-5 | 行情用 Parquet + DuckDB，交易用 SQLite | MongoDB / PostgreSQL / TimescaleDB | 单机零运维；DuckDB 列存查询快；SQLite WAL 足够单账户写入。**预留 Postgres 适配** |
| ADR-6 | 编排用 LangGraph | 自研状态机 / CrewAI | 与 TradingAgents-CN 一致，生态成熟，支持检查点与流式 |
| ADR-7 | 执行层复用 qmt_etf 的连接管理 | 从零写 xtquant 封装 | 已跑通实盘，省掉踩坑成本 |
| ADR-8 | LLM 结构化输出用 Pydantic Schema + 校验重试 | 正则/长度判定 | 修正 TradingAgents-CN 的 `len(report)>100` 缺陷 |

### 4.3 运行时序（交易日）

| 时间 | 阶段 | 动作 | 是否用 LLM |
|---|---|---|---|
| 每日 06:30 | 数据同步 | 增量拉取日线/财务/新闻/公告/龙虎榜，重算因子 | 否 |
| 07:30 | 市场状态识别 | 计算 Regime（趋势/震荡/风险），确定当日总仓位上限 | 否 |
| 08:00 | L0+L1 选股 | 全市场粗筛 → 因子打分 → Top 100 候选池 | 否 |
| 08:15 | **L2 LLM 研判** | 多智能体分析 Top 100 → 输出 ≤10 个 `TradeIntent` | **是** |
| 09:00 | 计划固化 | Intent → 风控预检 → 仓位计算 → 生成 `TradePlan`（含触发条件） | 否 |
| 09:15–09:25 | 集合竞价 | 竞价异动监控，对计划做最后一次校正（不新增标的） | 否 |
| 09:30–15:00 | 盘中执行 | 按计划触发下单；持仓守护（止损/移动止盈/时间止损/熔断） | 否 |
| 盘中事件触发 | 快速通道 | 突发公告/异动/黑天鹅 → LLM 快速评估（超时 30s 则降级为规则处理） | **是（有降级）** |
| 15:00 | 收盘对账 | 与券商流水对账，持仓/资金校验 | 否 |
| 16:00 | **盘后复盘** | 逐笔归因、经验入库、绩效更新 | **是** |
| 每周日 | 进化 | Walk-forward 参数寻优、策略池调权、影子盘评估 | 部分 |

## 6. 详细设计

### 6.1 L0 数据层（DataHub）

#### 6.1.1 数据源分工

| 数据类型 | 主源 | 备源 | 频率 | 说明 |
|---|---|---|---|---|
| 实时 Tick / 盘口 | QMT `xtdata.subscribe_quote` | — | 实时推送 | 唯一可靠的盘中源 |
| 分钟 K 线 | QMT `get_market_data_ex` | AkShare | 盘中/日终 | |
| 日 K（前复权） | QMT | Tushare → AkShare | 每日 | 复权方式必须统一，**回测用后复权，展示用前复权** |
| 财务报表 | Tushare | AkShare | 季度 | **必须按公告日（ann_date）而非报告期入库** |
| 股本/流通盘/行业 | Tushare | AkShare | 每日 | |
| 新闻 | AkShare | RSS/自建爬虫 | 实时/日内 | 必须带 `publish_time` |
| 公告 | AkShare（巨潮） | Tushare | 实时 | 带 `ann_time` |
| 龙虎榜 / 资金流 | Tushare | AkShare | 日终 | |
| 涨跌停/停复牌 | QMT + Tushare | AkShare | 每日 | 风控必需 |
| 指数/板块 | QMT | Tushare | 每日 | Regime 判定用 |

#### 6.1.2 统一接口

```python
class DataHub:
    def get_bars(self, symbols, freq, start, end, adjust="hfq", asof=None) -> pl.DataFrame: ...
    def get_fundamentals(self, symbols, fields, asof) -> pl.DataFrame: ...
    def get_news(self, symbols=None, start=None, end=None, asof=None) -> list[NewsItem]: ...
    def get_events(self, symbols, start, end, asof=None) -> list[Event]: ...
    def get_instrument(self, symbol) -> InstrumentProfile: ...
    def get_realtime(self, symbols) -> dict[str, Tick]: ...
```

**所有接口都有 `asof` 参数**，这是 PIT（Point-in-Time）的实现基础。回测时 `asof = 回测当前时刻`，任何 `publish_time > asof` 的数据一律过滤掉。这是防未来函数的第一道防线，`datahub/pit.py` 统一实施。

> 修正 TradingAgents-CN：它的数据接口没有 `asof` 概念，因为它根本不回测。这是我们必须从第一行代码就带上的设计。

#### 6.1.3 降级与熔断

借鉴 `data_source_manager.py` 的优先级降级，但增加：

- 每个源维护健康度（成功率、延迟、连续失败数）
- 连续失败 N 次 → 熔断 M 分钟，自动切备源
- 全部源失败 → 抛 `DataUnavailableError`，触发 P4 失败安全（当日停止开仓）
- 数据质量校验：涨跌幅 > 板块限制、成交量为 0、价格为 0/负、缺失率超阈值 → 标记脏数据并告警

#### 6.1.4 缓存策略（修正 TradingAgents-CN 的 TTL 错配）

| 数据 | 缓存层 | TTL |
|---|---|---|
| 实时 Tick | 内存 | **不缓存**，直接用 QMT 推送 |
| 分钟 K（当日） | 内存 | 60 秒 |
| 日 K（历史） | Parquet | 永久，按日增量追加 |
| 财务数据 | Parquet | 永久（PIT 快照，只追加不修改） |
| 新闻/公告 | SQLite | 永久（带 publish_time） |
| 因子值 | Parquet | 永久 |
| LLM 响应 | SQLite | 永久（回测重放用） |

### 6.2 L1 特征层

#### 6.2.1 因子库

分四大类，每个因子是一个独立可测试的函数，产出标准化后的截面分位值：

| 类别 | 示例因子 |
|---|---|
| 量价动量 | 20/60 日收益率、换手率变化、量比、突破强度、ATR、乖离率、均线多头排列 |
| 资金流 | 主力净流入（5/10 日）、大单占比、北向持股变化、龙虎榜净买额 |
| 基本面 | ROE、营收/净利同比、毛利率变化、PE/PB 行业分位、经营现金流质量 |
| 情绪与题材 | 概念板块热度、新闻情感分、研报评级变化、互动易活跃度、涨停连板梯队 |

设计要点：
- 因子计算全部**向量化 + 严格 PIT**，任何用到未来数据的因子在单测中必须被检出
- 因子值落 Parquet，回测时直接读，不重算
- 提供 `因子有效性检验`（IC、IR、分层回测），新因子必须通过检验才能进入打分

#### 6.2.2 市场状态识别（Regime）

这是 qmt_etf 和 TradingAgents-CN 都没有的。作用是**在系统层面控制总仓位**，比任何个股择时都重要。

输入：指数（上证/创业板）均线结构、波动率（ATR/历史波动）、市场宽度（涨跌家数比、创新高家数）、成交额趋势、涨停/跌停家数比。

输出：

| Regime | 判定 | 总仓位上限 | 新开仓限制 |
|---|---|---|---|
| `TREND_UP` | 指数站上 20/60 日线，宽度健康 | 80% | 正常 |
| `RANGE` | 震荡，无明显方向 | 50% | 仅高分标的 |
| `TREND_DOWN` | 指数破位，宽度恶化 | 20% | 仅特殊事件驱动 |
| `RISK_OFF` | 极端波动/系统性风险 | 0%（只平不开） | 禁止 |

【待确认】Regime 判定的具体阈值需要用历史数据标定，评审后进入 M1 实现。

### 6.3 L2-a 选股漏斗（不依赖 LLM）

这是 ADR-3 的落地。核心目的：**把 LLM 的工作量从 5000 只压到 100 只以内**。

```
全市场 ~5400 只
   │
   ├─ L0 硬过滤（规则，零成本）
   │    · ST/*ST/退市整理  · 上市 < 60 日  · 停牌
   │    · 当日一字涨停/跌停（买不进/卖不出）
   │    · 20日均成交额 < 5000万（流动性不足，冲击成本高）
   │    · 市值 < 20亿（壳/操纵风险）  · 黑名单（财务造假/监管处罚）
   │    ↓ 约 1500–2500 只
   │
   ├─ L1 因子打分（向量化，秒级）
   │    综合分 = Σ(因子分位 × 权重)，权重按 Regime 动态调整
   │    ↓ 取 Top 100（含行业分散约束：单行业 ≤ 15 只）
   │
   └─ L2 LLM 深度研判（见 6.4）
        ↓ 输出 ≤ 10 个 TradeIntent
```

**成本估算**：Top 100 × 约 25k tokens/只 ≈ 2.5M tokens/日。按 DeepSeek/Qwen 的价格，日成本约 ¥5–20，可接受。若用 GPT-4 级模型会到 ¥300+/日，**建议深度模型只用于最终 Top 20，浅层模型跑前 80**（借鉴 TradingAgents-CN 的 `deep_think_llm` / `quick_think_llm` 双档设计）。

### 6.4 L2-b LLM 决策层

#### 6.4.1 对 TradingAgents-CN 的五处关键改造

| 原设计 | 问题 | 新设计 |
|---|---|---|
| 四分析师串行 | 延迟叠加 | **并行 fan-out → fan-in**，延迟降约 60% |
| `len(report)>100` 判完成 | 质量无保障 | **Pydantic Schema 校验 + 字段完整性检查 + 最多 2 次重试** |
| 辩论历史字符串拼接 | token 线性膨胀 | **结构化 `list[DebateTurn]`**，可裁剪、可检索 |
| 单票视角 | 无法做组合决策 | 新增 **`PortfolioState`**（现有持仓、可用资金、行业暴露、当日已开仓数） |
| 风控辩论员无 memory | 无经验积累 | 风控层改为**规则引擎为主 + LLM 补充**，LLM 只负责发现规则覆盖不到的风险 |

#### 6.4.2 智能体拓扑

```
                    ┌──────────────────────────────┐
                    │ FactPack Builder (非LLM)      │
                    │ 把结构化数据整理成"事实卡片"    │
                    │ 显式标注数据日期，防幻觉        │
                    └──────────────┬───────────────┘
                                   │
        ┌────────────┬─────────────┼─────────────┬────────────┐
        ▼            ▼             ▼             ▼            │ 并行
  技术面分析师   基本面分析师    资金面分析师   消息面分析师      │
        └────────────┴─────────────┼─────────────┴────────────┘
                                   ▼
                          ┌─────────────────┐
                          │  事实校验器 ★   │  数字与 FactPack 比对
                          │  (非LLM)        │  不一致 → 打回重做
                          └────────┬────────┘
                                   ▼
                       多空辩论（结构化，1–3 轮动态）
                       低置信度自动加轮，高一致性提前结束
                                   ▼
                          研究主管：形成投资论点
                                   ▼
                       组合经理（输入 PortfolioState）
                       考虑：与现有持仓相关性/行业集中度/资金占用
                                   ▼
                       风险官（LLM）：列举风险点与失效条件
                                   ▼
                       ┌──────────────────────┐
                       │  TradeIntent (JSON)  │ → 交给 L3 风控与仓位
                       └──────────────────────┘
```

**FactPack Builder** 和 **事实校验器** 是本设计相对 TradingAgents-CN 的重要增量：
- FactPack 把「PE=23.4（截至2026-08-07）、近20日主力净流入 1.2 亿、2026-08-05 发布中报预增公告」这类事实预先整理好喂给 LLM，减少 LLM 自己调工具算错的概率；
- 事实校验器把 LLM 输出中出现的所有数字抽出来，与 FactPack 比对，偏差超阈值直接判定为幻觉并重试。这在自动交易里是必需的安全阀。

#### 6.4.3 核心契约：TradeIntent

这是全系统最重要的数据结构，**补齐了 TradingAgents-CN 缺失的仓位、止损、时间、失效条件四类字段**。

```python
class TradeIntent(BaseModel):
    # 标的与方向
    symbol: str                        # 000001.SZ
    action: Literal["BUY", "SELL", "HOLD", "REDUCE", "ADD"]
    confidence: float                  # 0-1，LLM 主观置信度
    conviction: Literal["LOW","MEDIUM","HIGH"]   # 用于仓位分档

    # 入场（只给参考与触发条件，不给最终价格/数量）
    entry_type: Literal["MARKET_OPEN","LIMIT","BREAKOUT","PULLBACK"]
    entry_ref_price: float | None      # 参考价
    entry_trigger: str | None          # 结构化触发条件，如 "price>=12.35 and vol_ratio>=1.5"

    # 风险（必填，缺失则 Intent 无效）
    stop_loss_type: Literal["FIXED_PCT","ATR","STRUCTURE"]
    stop_loss_value: float             # pct 或 ATR 倍数或结构位价格
    take_profit: list[TPLevel]         # 分批止盈：[{price_or_pct, ratio}]
    risk_budget_hint: float            # 建议风险预算占总资产 %（0.3-1.5）
    max_weight_hint: float             # 建议单票权重上限 %

    # 时间
    time_horizon_days: int             # 预期持有天数
    max_holding_days: int              # 超时强制退出（时间止损）
    valid_until: date                  # Intent 本身的有效期

    # ★ 逻辑失效条件（TradingAgents-CN 没有，但自动交易必需）
    invalidation: str                  # "若中报业绩不及预期 / 板块指数跌破20日线，则论点失效"
    invalidation_checks: list[str]     # 可机器判定的部分

    # 可追溯性
    evidence: list[Evidence]           # 每条结论对应的数据来源与时间戳
    reasoning: str
    risk_flags: list[str]              # 如 ["高估值","解禁临近","商誉大"]
    agent_votes: dict[str, str]        # 各智能体的独立结论，用于事后归因
    prompt_hash: str                   # 回放用
    model_info: dict
```

**`invalidation` 是我特别想强调的设计**：真实交易中，出场理由不只有"跌到止损位"，更常见的是"当初买它的逻辑没了"。把这个逻辑显式写下来并尽量机器化（`invalidation_checks`），是持仓守护的重要输入。

#### 6.4.4 LLM 成本与可靠性控制

- **硬性成本熔断**：日/月预算上限，超限直接停用 LLM 层，系统降级为纯因子模式（P5 的价值体现）。修正 TradingAgents-CN 的 `COST_ALERT_THRESHOLD` 只告警不阻断的问题。
- **响应缓存**：`hash(model + prompt + temperature)` → response，落 SQLite。回测重放、失败重试、调试都受益。
- **超时与降级**：单节点超时（默认 60s）→ 重试 1 次 → 仍失败则该标的标记 `LLM_UNAVAILABLE`，**不产生 Intent**（而不是产生一个瞎猜的 Intent）。
- **温度设为 0**，追求可复现。
- **记忆不得静默降级**：修正 TradingAgents-CN 的 `self.enabled=False` 问题，embedding 不可用时**启动阶段直接报错**。

#### 6.4.5 LLM 独立管理与场景智能选模（重构落地）

**为什么独立**：参考 `ai-dev-ops` 的 LLM 管理模式，把 provider/模型/场景从 `settings.yaml` 与 `.env` 中剥离，
单独放到 `config/llm.yaml` 统一管理。收益：

- **可配多平台**：`deepseek` / `qwen` / `moonshot` / `openai` 等各 provider 独立 `base_url` + `api_key_env`（**只存环境变量名，Key 运行时从 `os.environ` 读，绝不落盘**）。
- **可配多模型**：每个模型绑定 provider，携带 `capabilities`（general/fast/cheap/reasoning/deep/code）、`context_window`、`price_per_1k_tokens`，成本按人民币 input/output 单价精确计费。
- **场景化智能选模**：声明「什么任务用什么模型」（`scenes`），如深度研判 `market_analysis`/`risk_assess` 偏好推理模型，快速分类 `quick_classify` 偏好便宜模型。

**相对 ai-dev-ops 的实质改进**：ai-dev-ops 的选模是「取第一个 capability 匹配的模型」，坏模型不会出局。
本系统 `ModelSelector` 改为**加权打分排序**：

```
score = capability_weight·cap + health_weight·hth + cost_weight·cst
cap  = 模型 capabilities 与场景 prefer 的匹配度（Jaccard）
hth = 健康度（熔断中=0；连续失败越多分越低）
cst = 单价越低分越高（按全模型均价归一）
```
默认 `capability_weight=0.40`、`health_weight=0.40`、`cost_weight=0.20`。这样：
- 推理场景**首选推理模型**（如 `deepseek-reasoner`），而非随机第一个；
- 便宜场景**首选低价模型**（如 `qwen-plus`）；
- **坏模型自动靠后**：某模型连续失败达阈值（默认 5 次）触发熔断（默认 300s），熔断期间 `score=0` 直接出局；恢复后重新入选。

**失败安全闭环（P4/P5 落点）**：

- **候选链 fallback**：`LLMManager.complete(prompt, scene=, model=)` 解析候选链（显式 `model` > 场景 `candidates` > `default_model`），
  主选调用失败（网络/限流/结构异常）自动尝试下一个；全部失败抛 `LLMCallFailed` → Agent 降级规则路径（P5）。
- **成本熔断**：日成本超 `budget.daily_cny`（默认 ¥30）抛 `LLMBudgetExceeded`，LLM 层停用、系统降级纯因子模式继续跑。
- **接不上就退 Mock**：缺 API Key / provider=mock / 找不到 `llm.yaml` / 配置损坏 → 整体退回 `MockLLM`，系统照常起（P5 不崩）。

> 与运维体检同源：监控告警用 `CostTracker.daily_budget` 计算「成本达预算 80% 告警」，避免两套预算口径不一致。

### 6.5 事件与新闻驱动

#### 6.5.1 事件分类与响应

| 事件类型 | 来源 | 响应 |
|---|---|---|
| 重大公告（重组/业绩预告/减持/立案调查） | 巨潮/AkShare 轮询 | **持仓标的**→立即触发 LLM 快速评估；候选标的→更新评分 |
| 突发新闻（行业政策/黑天鹅） | 新闻源 | 影响面判定 → 涉及持仓则评估 |
| 盘中异动（急跌/放量/触及关键位） | QMT tick 计算 | 先走规则（止损/加仓条件），必要时才调 LLM |
| 龙虎榜/大宗交易 | 日终 | 进入次日因子 |
| 指数级风险（大盘急跌、涨停潮反转） | 实时计算 | 直接触发 Regime 降级，可能触发 Kill Switch |

#### 6.5.2 快速通道设计（P2 的例外路径）

```
事件到达 → 去重(事件指纹) → 重要性打分(规则)
   ├─ 低：入库，次日盘前处理
   ├─ 中：更新因子/评分，不触发交易
   └─ 高：进入快速通道
        ├─ 是否影响持仓？否 → 加入观察
        └─ 是 → 【规则先行】立即执行确定性动作（如立案调查 → 直接减仓）
                 └─ 【LLM 后置】30s 超时内给出评估，用于后续决策
```

**关键原则：规则先行，LLM 后置。** 对于"立案调查""重大违规"这类确定性利空，不能等 LLM，规则直接动手。LLM 用于处理模糊事件。

### 6.6 L3 风控引擎（RiskEngine）

风控是本系统的安全核心，采用**三闸门 + 一开关**结构。所有规则可配置、可单测、可回溯，且**LLM 无权绕过**（P3）。

#### 6.6.1 Gate-1：交易前置闸门（Pre-Trade）

每一笔订单在发往 QMT 之前必须逐条通过，任何一条不过就拒单并记录 `RiskEvent`。

| 类别 | 规则 | 默认值 |
|---|---|---|
| **标的合规** | 非 ST/*ST/退市整理 | 强制 |
| | 非停牌 | 强制 |
| | 上市满 N 日 | 60 |
| | 不在黑名单 | 强制 |
| **可交易性** | 未一字涨停（买入时）/ 未一字跌停（卖出时） | 强制 |
| | 委托价在涨跌停区间内（按板块查 `InstrumentProfile`） | 强制 |
| | 预估成交量 ≤ 近 20 日均量的 X% | 5% |
| **仓位约束** | 单票市值占比 ≤ | 15% |
| | 单一行业占比 ≤ | 30% |
| | 总仓位 ≤ Regime 上限 | 动态 |
| | 持仓标的数 ≤ | 10 |
| | 当日新开仓数 ≤ | 3 |
| | 与现有持仓 60 日相关性 > 0.8 的标的数 ≤ | 3 |
| **资金** | 可用资金充足（含手续费缓冲 0.5%） | 强制 |
| | 单笔金额 ≤ | 总资产 10% |
| **卖出** | 可卖数量校验（T+1，用 `m_nCanUseVolume`） | 强制 |
| **账户级** | 当日已实现+浮动亏损 ≤ | 总资产 2% |
| | 近 5 日累计回撤 ≤ | 5% |
| | 最大回撤 ≤（触发即 Kill Switch） | 15% |
| **执行防护** | 通过 `OrderGuard` 幂等/防重检查 | 强制 |
| **系统健康** | 数据源正常、QMT 已连接、账户已对账 | 强制 |

> 数值均为初始建议值，需在 M1 回测中标定。【待确认】

#### 6.6.2 Gate-2：持仓守护（In-Trade，盘中常驻）

借鉴 `chanlun_strategy.py::_determine_trade_action` 的**优先级链**设计，但扩展为组合级。守护进程每个 tick（或每 3 秒）对全部持仓求值，按优先级从高到低，命中即执行并跳出：

```
1. 账户级熔断        当日亏损超限 / 最大回撤触线  → 全部平仓，停止开仓
2. 强制风控          个股触发停牌前异动 / 立案调查等黑天鹅  → 立即市价卖出
3. 移动止盈          盈利 ≥ 激活阈值 后，从最高价回撤 X%  → 卖出
4. 固定止损          跌破 entry - stop_loss  → 卖出
5. 时间止损          持有天数 > max_holding_days  → 卖出
6. 逻辑止损 ★        invalidation_checks 命中  → 卖出
7. 分批止盈          触及 TPLevel  → 按 ratio 卖出
8. 计划触发          entry_trigger 满足且通过 Gate-1  → 买入
```

**第 6 条「逻辑止损」是 qmt_etf 完全没有的**，它把 LLM 给出的失效条件真正接入了执行环路，是 LLM 层价值落地的关键一环。

止损的具体形式支持三种（由 Intent 指定）：
- `FIXED_PCT`：固定百分比（简单，但不适应不同波动率的股票）
- `ATR`：`entry - k × ATR(14)`（**推荐默认**，自适应波动率）
- `STRUCTURE`：结构位（前低/均线/箱体下沿）

#### 6.6.3 Gate-3：盘后校验（Post-Trade）

- **对账**：本地订单/成交/持仓 vs `query_stock_asset` / `query_stock_positions` / `query_stock_trades`，不一致立即告警并**次日禁止开仓**直到人工确认
- **异常检测**：滑点异常（实际成交价偏离预期超阈值）、成交率异常、重复成交、未预期持仓
- **绩效归因**：见 6.11

#### 6.6.4 Kill Switch

三种触发方式：自动（账户回撤触线/对账失败/连续下单异常）、定时（超出交易时段）、手动（CLI 命令 / 消息指令）。

三档模式：

| 模式 | 行为 |
|---|---|
| `NORMAL` | 正常交易 |
| `REDUCE_ONLY` | 只允许平仓，禁止开仓（**默认的失败安全状态**） |
| `FLATTEN` | 立即平掉所有持仓并停机 |

P4 的落地：任何未预期异常，系统自动切到 `REDUCE_ONLY`，绝不"猜着继续交易"。

### 6.7 L3 仓位管理（PositionSizer）

抛弃 qmt_etf 的固定比例法（`total_asset*0.7`、`*0.1`），改用**风险预算法**——这是专业交易系统的标准做法，核心思想是"每笔交易亏钱的金额恒定，而不是买入的金额恒定"。

#### 6.7.1 计算流程

```
Step 1  基础风险预算
        risk_amount = total_asset × base_risk_pct          # base_risk_pct 默认 0.6%

Step 2  置信度调整
        risk_amount ×= conviction_factor                    # LOW 0.6 / MEDIUM 1.0 / HIGH 1.4

Step 3  Regime 调整
        risk_amount ×= regime_factor                        # UP 1.0 / RANGE 0.7 / DOWN 0.4 / RISK_OFF 0

Step 4  按止损距离反推股数
        stop_distance = entry_price - stop_loss_price
        raw_shares    = risk_amount / stop_distance

Step 5  多重上限裁剪（取最小）
        · 单票市值上限:  total_asset × max_weight_pct / entry_price
        · 可用资金上限:  available_cash × 0.95 / entry_price
        · 流动性上限:    avg_volume_20d × 5% 
        · 组合总仓位剩余额度

Step 6  A股取整
        shares = floor(shares / 100) × 100
        if shares < 100: 放弃该笔交易（记录原因）
```

**为什么这样设计**：假设总资产 100 万，`base_risk_pct=0.6%`，则每笔最多亏 6000 元。若 A 股止损距离 3%，则买入 20 万；若 B 股波动大止损距离 8%，则只买 7.5 万。这样两笔交易的**风险敞口是相等的**，而不是金额相等。这直接解决了 qmt_etf 中"高波动股票和低波动股票买一样多"的问题。

#### 6.7.2 组合层约束

- 总风险预算：所有持仓的 `Σ(当前价 - 止损价) × 持股数` ≤ 总资产 × 3%
- 行业风险预算：单行业 ≤ 总资产 × 1.2%
- 相关性惩罚：新标的与现有持仓相关性高时，`risk_amount` 打折

#### 6.7.3 关于 Kelly

【待确认】是否引入 Kelly。我的建议是**不用完整 Kelly**：Kelly 对胜率和赔率的估计误差极其敏感，而我们的胜率估计本身就不可靠。若要用，只用**分数 Kelly（≤ 0.25 倍）**作为 `conviction_factor` 的补充参考，且必须有上限保护。

### 6.8 L4 执行层

#### 6.8.1 分层结构

```
TradePlan ──▶ ExecutionService ──▶ OrderGuard ──▶ Gateway(抽象) ──┬─▶ QMTGateway    (实盘)
                    │                   │                        └─▶ SimGateway    (回测/模拟)
                    │                   └─ 幂等键/防重/冷却/挂单管理
                    └─ 拆单/价格决策/超时重试/部分成交处理
```

**Gateway 抽象是 P7 的关键**：回测和实盘走完全相同的 `ExecutionService` 和 `OrderGuard`，只在最底层换网关。这从结构上杜绝了 qmt_etf 中"回测不算滑点、实盘算"的失真问题。

#### 6.8.2 QMTGateway（复用 + 补齐）

**直接复用** `qmt_etf/utils/qmt_connection_manager.py` 的单例连接骨架：`XtQuantTrader(QMT_PATH, session_id)` → `start()` → `connect()` → `subscribe(account)`。

**必须补齐的四项**：

1. **断线重连**（qmt_etf 的 `on_disconnected` 只有一行 warning 日志）
   ```
   on_disconnected() 
     → 置 is_connected=False
     → 立即切 REDUCE_ONLY，暂停所有新订单
     → 指数退避重连（1s,2s,4s...最大60s，无限重试）
     → 重连成功 → 重新 subscribe → 【强制全量对账】→ 恢复 NORMAL
   ```
   重连后**必须对账**：断线期间可能有成交回报丢失，本地状态已不可信。

2. **`InstrumentProfile` 板块差异表**（qmt_etf 只在选股层区分，下单层没有）
   | 板块 | 代码前缀 | 涨跌幅 | 最小变动 | 备注 |
   |---|---|---|---|---|
   | 主板 | 60/00 | ±10% | 0.01 | |
   | 创业板 | 300 | ±20% | 0.01 | 需权限 |
   | 科创板 | 688 | ±20% | 0.01 | 需权限，最小 200 股起 |
   | 北交所 | 43/83/87/92 | ±30% | 0.01 | 本期**排除** |
   | ST | — | ±5% | 0.01 | 本期**排除** |
   | 新股首日 | — | 特殊 | — | 本期**排除** |

3. **价格策略**（qmt_etf 混用 FIX_PRICE 和 LATEST_PRICE，无统一规则）
   - 默认**限价单**（`FIX_PRICE`），买入价 = 卖一价 × (1 + 滑点容忍)，卖出价 = 买一价 × (1 - 滑点容忍)，滑点容忍默认 0.3%
   - 止损单用更激进的价格（买一下浮 1%）保证成交，宁可多滑点也要出来
   - 涨跌停价夹逼：`price = clip(price, limit_down, limit_up)`
   - 【待确认】是否使用 `MARKET_PEER_PRICE_FIRST`（对手方最优价）——需确认券商支持情况

4. **订单状态机与超时**
   ```
   PENDING → SUBMITTED → PART_FILLED → FILLED
                      ↘ REJECTED   ↘ CANCELLED
   ```
   - 限价单挂单超时（默认 60s，借鉴 qmt_etf 的 `check_pending_order`）→ 撤单
   - 撤单后按剩余量决策：追价重下（最多 2 次）或放弃
   - 部分成交必须正确更新持仓和剩余计划量

#### 6.8.3 OrderGuard（提取自 chanlun_strategy 并强化）

把 `chanlun_strategy.py::execute_trade` 里那套已被实盘验证的三道防线抽象成独立服务，并按 `account + symbol` 维度管理状态（修正原来放在策略实例里、多标的会串扰的问题）：

| 防线 | 原实现 | 新实现 |
|---|---|---|
| 挂单未决拦截 | `if self.pending_order: return`，60s 超时清除 | 按 symbol 维护 pending 集合，超时可配 |
| 同类型冷却 | 120s 内同 signal 不重复 | 冷却时间按信号类型配置（止损类不冷却） |
| 临时 ID 占位 | 下单前置 `'pending_stop_loss'`，成功后替换 | 改为**幂等键**：`hash(plan_id + symbol + side + date + seq)`，落库唯一索引 |
| — | 无 | 新增：单标的日内下单次数上限 |
| — | 无 | 新增：全局每秒订单速率限制 |
| — | 无 | 新增：**下单前最后一次账户余额/持仓核对** |

幂等键是关键升级：即使进程崩溃重启、回调重复触发，同一个幂等键也只会产生一笔订单。

#### 6.8.4 成本模型（回测实盘共用）

```python
佣金     = max(成交额 × 0.025%, 5元)      # 双边，【待确认】实际费率
印花税   = 成交额 × 0.05%                 # 仅卖出
过户费   = 成交额 × 0.001%                # 沪深双边
滑点     = f(委托量/近20日均量, 波动率, 买卖方向)   # 分档，非固定值
```

滑点模型是回测真实性的命门。建议做法：**M1 用保守固定滑点（0.2%）先跑通，M3 模拟盘期间用真实成交数据回归标定滑点函数**，再回灌到回测。

### 6.9 L4 回测引擎（BacktestEngine）— P7 实盘同代码路径

> **设计铁律 P7：回测与实盘走同一套执行链路。** 回测不是另写一套模拟成交，而是把实盘的执行层（Gateway / CostModel / OrderGuard / RiskEngine / PositionSizer / PortfolioState）原样复用，只把 `SimGateway` 换掉 `QmtGateway`。这样回测里验证过的风控、仓位、成本模型，实盘一字不差地生效。

#### 6.9.1 引擎装配

`BacktestEngine(settings, hub, *, initial_cash, top_n, max_holding_days, fixed_start, brain)`：

- `hub`：`DataHub`，回测从同一数据源取历史行情/财务/新闻，**禁止在回测里偷偷接未来数据**（P6 可复现）。
- `brain`：`BrainGraph | None`。为 `None` 时走 `intent_from_rank` 的**纯因子路径**（P5 默认、零成本）；传入 `BrainGraph` 则由多智能体产出 `TradeIntent`。**两条路径下游完全一致**——这正是 P7 的验证点：换脑不换执行链路。
- 内部复用组件与实盘完全一致：`CostModel`、`KillSwitch`、`RiskEngine`、`PositionSizer`、`OrderGuard`、`PortfolioState`、`ExecutionService(SimGateway)`。

#### 6.9.2 主循环（与交易日时序对齐）

`run(start, end) -> BacktestResult`：

1. 取交易日序列，不足 3 天直接返回（数据不足）。
2. 每日：
   - `_derive_loss_limits()`：由权益曲线派生当日/近 5 日亏损，喂给风控熔断线（修正「执行滞后」导致的误熔断）。
   - `portfolio.mark_t1(next_day)`：解锁隔夜仓（T+1），使 Gate-1「可卖数量校验」能放行。
   - **Gate-2 持仓守护**：用 T 日 bar 判定 `risk.guard_positions(...)`，触发止损/止盈/熔断减仓。
   - **选股 + 决策**：`pipeline.run` → `brain.run`（或纯因子）→ 产出 `TradeIntent` 列表。
   - **执行**：`exec_svc.submit` 经 `OrderGuard` 四道闸门（P1 权限 / 可卖数量 / 涨跌停 / 风控预算）落到 `SimGateway`，按 T 日收盘价 + 成本模型撮合。
3. 汇总 `BacktestResult`：权益曲线、成交明细、各档 KillSwitch 触发次数、LLM 调用数/成本。

#### 6.9.3 成本与真实性建模

- `CostModel.from_settings`：佣金、印花税、滑点（按成交量冲击）、最小手续费，与实盘同配置。
- `SimGateway`：**当日收盘价成交**（非未来函数），含涨跌停/停牌跳过、T+1 限制。
- 所有随机源（如有）由 `fixed_start` 派生确定性种子 → P6 可复现。

#### 6.9.4 评估指标

`metrics.performance(equity, *, periods_per_year=252)`：年化收益、 Sharpe、最大回撤、胜率、盈亏比、换手率。`BacktestResult` 自带 `details` 便于断言与 CLI `report` 渲染。

### 6.10 L4 策略进化（Evolution）

> **设计原则**：进化不是「让 LLM 自己改自己」，而是**对可解释的参数空间做walk-forward 优化 + 策略池动态权重 + 复盘归因**。LLM 只在决策层提供语义，进化层是纯数学/统计，结果可审计、可回滚。

#### 6.10.1 Walk-Forward 优化器（WalkForwardOptimizer）

`optimizer.py`：

- `Window`：一个 (in-sample 训练, out-of-sample 验证) 切片。
- `make_windows(start, end)`：把历史切成多个不重叠窗口，避免前视偏差。
- `grid(space)`：参数网格生成；`run(space, start, end, *, brain=None)`：逐窗口在 IS 上寻优、在 OOS 上验证。
- **过拟合检测**（核心防骗）：`ParamScore` 记录 `mean_oos / std_oos / worst_oos / overfit_gap`；`robust_score(stability_penalty=0.5)` 用 OOS 均值扣减 OOS 波动，OOS 越稳、IS/OOS 差距越小，分数越高。
- `clamp(old, new)`：新参数相对旧参数的**最大变动幅度封顶**，防止一次进化把策略打飞（工程护栏）。

#### 6.10.2 策略池（StrategyPool）

`pool.py`：

- `StrategyRecord`：单策略的滚动收益序列（Ring buffer）。
- `StrategyPool.register(name, *, params, meta)` / `record(name, ret)` / `record_batch` / `retire(name, reason)`：策略的注册、贡献记账、下线。
- `rebalance(asof) -> RebalanceResult`：按近 N 期滚动收益做**风险平价式权重再平衡**，连续亏损超阈值自动降权/暂停（与 KillSwitch 解耦但互补）。
- `snapshot() / load()`：池状态序列化，支持跨进程/重启续做。

#### 6.10.3 复盘归因引擎（ReviewEngine）

`review.py`：

- `TradeAttribution`：单笔交易的 `win`、`cost_drag`（成本拖累）、持仓天数、触发因子。
- `Lesson`：从复盘提炼的「什么环境下该/不该做」，结构化（`render()` 可达人读）。
- `ReviewEngine.review(asof) -> ReviewResult`：把成交明细 + 行情 + 因子暴露做归因，输出「赚钱靠什么、亏钱踩了什么」，供 `evolve` 任务消费。

### 6.11 运维与监控（Ops）

> **设计原则 P4（失败安全）**：通知通道、监控、报告**任何一环异常都不能带崩主交易流程**。监控发现风险 → 拉闸（KillSwitch）是最高优先级动作；通知失败只是「没告诉你」，系统照样该停就停。

#### 6.11.1 健康监控（HealthMonitor / Watchdog）

`monitor.py`：

- `CheckResult`：`name / ok / severity / detail / blocking`。`blocking=True` 的检查失败会直接拉闸。
- `HealthMonitor.register(name, fn)` / `check(asof, *, notify=True) -> HealthReport`：注册心跳式检查（数据源连通、DB 可写、KillSwitch 状态、持仓与账户一致性、成本预算余量等），`failed()` 列出失败项，`healthy` 给出整体结论。
- `heartbeat(component)`：组件存活打点；`Watchdog` 监控「关键组件多久没心跳」，超时判定假死。
- `trading_window_guard(now, killswitch, *, ...) `：交易时段护栏——非交易时段/休市禁止下单动作。

#### 6.11.2 通知（Notifier）

`notify.py`：

- `Level`（INFO/WARN/ERROR/CRITICAL）+ `Message`；`Channel` 抽象：`ConsoleChannel`（默认，永不失败）、`MemoryChannel`（测试/内存）、`FileChannel`、`WecomChannel` / `DingTalkChannel`（Webhook）。
- `Notifier.send(level, title, body, *, channels=None)`：**单通道异常不影响其他通道**，全部失败也不抛（P4）。
- `build_notifier(settings)`：按配置装配通道；未配置 webhook 时静默退化为 Console。

#### 6.11.3 报告（Reporter）

`report.py`：

- `DailyReport` / `WeeklyReport`：由权益、成交、风控事件、成本、LLM 调用量渲染 Markdown。
- `Reporter`：统一编排「收盘后日报 / 周报 / 复盘推送」，经 Notifier 发出。

### 6.12 调度层（Scheduler）

> **职责**：把「交易日该做什么、什么时间做、失败了怎么办」集中编排。**调度层只负责「按时触发 + 异常留痕 + 失败安全」，不持有任何业务逻辑**——业务逻辑全在 `JobRunner` 的方法里（§6.12.2）。

#### 6.12.1 JobRunner 与 @job 装饰器

`jobs.py`：

- `@job(name, *, critical=None)`：包裹每个任务方法。被调任务抛异常时**捕获并转 `JobResult(ok=False, reason=...)`**，绝不向上炸；同时自动写入运行日志表（支持重启续做，见 §6.12.3）。
- `JobResult`：`name / ok / reason / started_at / finished_at / trade_date`。
- `JobRunner`：持有全部组件（从 `TradingContext` 注入），每个方法对应一个任务。

#### 6.12.2 任务清单（JOB_MAP）

| 任务名 | 方法 | critical | 触发时机 | 职责 |
|---|---|---|---|---|
| `data_sync` | `data_sync` | **是** | 盘前 | 行情/财务/新闻同步入 PIT |
| `regime` | `regime` | 否 | 盘前 | 市场状态（牛/熊/震荡）判定 |
| `selection` | `selection` | 否 | 盘前 | 选股漏斗 → 候选池 |
| `research` | `research` | 否 | 盘前 | LLM 多智能体研判 → Intent |
| `plan` | `plan` | 否 | 盘前 | 风控+仓位 → 当日交易计划 |
| `auction_check` | `auction_check` | 否 | 集合竞价 | 开盘前最后一道持仓守护 |
| `intraday` | `intraday_tick` | **是** | 盘中 | 实时监控+执行+动态减仓 |
| `reconcile` | `reconcile` | **是** | 盘后 | 账户 vs 本地持仓对账 |
| `review` | `review` | 否 | 盘后 | 复盘归因（喂进化） |
| `evolve` | `evolve` | 否 | 盘后/周末 | walk-forward 优化+策略池再平衡 |
| `health` | `health` | 否 | 周期 | 健康检查+通知 |

`run_job(runner, name)`：按名执行单个任务，名字非法返回失败结果而非抛异常（CLI / 手动触发入口）。

#### 6.12.3 CRITICAL_JOBS 与失败安全（P4）

```python
CRITICAL_JOBS = frozenset({"data_sync", "reconcile", "intraday"})
```

- 关键任务失败 → `JobRunner` 自动 `killswitch.engage("任务 <name> 失败", manual=False)`，把系统降到 **REDUCE_ONLY**（停止开新仓、只减仓/守护），而非放任裸奔。
- 任务状态落库（`system_state`），**重启后可续做**——已成功的不重做，失败的可重试。
- 非关键任务失败只告警、不拉闸。

#### 6.12.4 TradingScheduler（APScheduler 封装 / 内置退化）

`runner.py`：

- `JobSpec`：任务名 + 触发时间（HH:MM）+ 是否交易日依赖。
- `TradingScheduler`：优先用 `APScheduler`（若装了）；**未安装则退化为内置轮询**（不强制依赖，降低部署门槛）。
- `next_run_at(spec, now)`：计算下一触发点，配合交易日历跳过休市。
- 支持 `plan_only`（只打印日程不执行）与 `simulate_day`（压缩时间跑完一整天流程）——CLI 的 `--plan-only` 与 `run` 同源。

#### 6.12.5 CLI（命令面）

`cli.py` 子命令：`run`（按模式跑调度）/ `select`（仅选股）/ `backtest`（回测）/ `report`（报告）/ `reconcile`（对账）/ `health`（体检）/ `killswitch`（人工拉闸/恢复）/ `evolve`（进化）。

- **真实下单需显式 `--mode live`**（默认 `sim`/`paper`），杜绝误触实盘。
- `killswitch`：显式改档（engage/flatten/reset）标记 `manual=True` 并持久化；纯查询返回健康度退出码（0=正常，非0=异常）——与 §6.11 的体检打通。
